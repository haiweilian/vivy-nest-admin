# Vivy Fullstack CRUD

按业务需求实现可接入项目的 CRUD。基础开发约定见仓库根目录 [AGENTS.md](../../../AGENTS.md)，具体接口和类型以当前源码为准。

## 默认决策

- 优先参考最接近的现有业务模块，按当前需求补齐业务判断、界面和接入工作。
- 新模块默认使用 TypeORM Repository；连表、聚合、动态条件先考虑 QueryBuilder。只有任务明确指定 MyBatis/XML、明确需要复用既有 XML SQL，或明确选择以 XML 组织 SQL 时，才新增 Mapper/XML。手写 SQL 或出现连表本身不构成启用 XML 的理由。
- 修改已有模块时保留其实际数据访问方式，按差异修改已有文件。
- 按用户范围实现：前端任务使用现有 API，后端任务处理接口与必要的模块接入；完整业务才组合前后端。不要把单层任务扩成全栈建设。
- 搜索项、展示列、编辑项、校验与操作由业务语义决定。树结构、主从表、导入导出、文件上传、数据权限等仅在需求需要时加入。

## 先确定业务约定

从用户说明和现有实现整理：业务位置与命名、已有或新增的数据结构、主键与字段类型、允许的操作、筛选与分页、唯一性或关联约束、权限命名空间、需要的交付范围。

自然语言、SQL、实体、DTO 和页面都可作为输入。缺失信息可从目标模块和项目惯例确定时直接推进；会改变业务行为的关键信息仍不明确时，只询问该缺口，并继续不依赖答案的工作。

## 实现与接入

1. 定位目标模块、消费者及最接近的现有范例，简要说明采用的业务约定和文件范围。
2. 先保持数据结构、可写字段、接口及返回类型一致，再完成要求的后端或前端实现。
3. 补齐该范围所需的模块注册、权限码、菜单映射、类型声明和 SQL 工件。已有业务采用增量修改。
4. 完成相关验证，说明具体实现、检查结果及运行环境尚未验证的内容。

用户要求实现时，持续推进到可审查的代码和接入结果。一次 CRUD 任务不默认修改全局认证或公共数据范围策略。

## 完成标准

- 用户要求的操作及业务约束实际生效，字段在数据库、DTO、API 和页面之间保持一致。
- 模块可被应用加载；菜单组件能映射到页面；实际请求涉及的权限码均有对应配置。
- 查询、分页、表单初始化和提交遵循项目现有协议；需要的数据范围同时覆盖相关读写路径。
- 没有额外引入未使用的 Mapper/XML、无需求的扩展或不必要的配置变更。
- 检查与交付说明匹配实际改动范围。
