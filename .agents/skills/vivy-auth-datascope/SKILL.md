# Vivy 权限与数据范围

基于项目已有的 SecurityModule、Redis 登录会话、SecurityContext 和 DataScopeModule 完成访问控制。基础约定见 [AGENTS.md](../../../AGENTS.md)，权限语义以当前源码为准。

## 先识别问题所在

分别确认：请求是否有有效身份、用户能否执行该动作、目标记录是否在允许的数据范围。菜单或按钮显示情况只能证明对应界面状态，不能替代后端授权结论。

明确本次目标：新增访问控制、修复某条越权路径、调整角色/数据范围，或排查权限不生效。一次任务按目标修改必要的链路；不自动创建全套 CRUD、改写全局权限体系或扩成全站安全审计。

## 关键约定

- 功能权限复用 `@RequirePermissions` / `@RequireRoles` 与 AuthService；普通业务保持项目权限码和异常响应协议。
- 服务端角色、权限和范围来自登录会话及服务端数据；请求中的用户、部门或 SQL 条件不是可信授权依据。
- 数据范围须实际进入查询与相关写入校验。`@DataScope` 元数据本身不会约束独立 Repository 操作。
- 新增业务的范围要求按明确需求决定；现有模块的详情、导出、批量更新和删除不能因列表已过滤而被视为已保护。
- 保留超级用户 ID、超级角色 ID、`admin` 角色编码和 `*:*:*` 权限编码的各自语义。
- 需要手写 SQL 或数据范围不自动启用 Mapper/XML。只有任务明确需要 XML 时才新增相关文件。

## 实施方式

1. 沿实际请求路径定位 Controller、守卫、会话读取、Service 查询/写入及相关前端调用；核对当前身份与所需权限。
2. 将用户要求与当前行为区分清楚。对没有运行验证的行为，以源码证据说明，避免把现有实现直接当成正确策略。
3. 实现符合目标的访问控制与必要的前端接入；保持项目现有接口和错误协议。
4. 验证允许和拒绝两条路径，尤其是直接 API 调用、范围外 ID 及批量混合目标。

现有空角色、未知范围或缺少元数据的处理不能被臆测成“默认拒绝”。任务要求修复这些路径时明确采用的策略，并验证不会意外放宽权限。

## 完成标准

- 后端实际执行功能权限与需要的数据范围控制，拒绝路径不会继续产生写入副作用。
- 权限码、菜单、类型声明、页面请求和角色关联一致；保留目标业务的授权边界。
- 验证真实可访问记录和副作用，不以按钮隐藏、SQL 文本或构建通过代替授权行为证明。
